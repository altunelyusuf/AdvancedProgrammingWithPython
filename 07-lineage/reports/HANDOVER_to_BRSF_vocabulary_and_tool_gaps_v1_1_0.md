# Handover to BRSF: tool gaps met while running a narrow lineage (2026-11-26)

From the session that ran a six-chapter-correction lineage on a course-materials register. My own fault first: I wrote small scripts to move register states instead of asking BRSF for a tool. They are listed so BRSF can decide what to adopt; they are in `08-tooling/lineage12-closure/` and `08-tooling/` of the course repository.

1. **State moves on a merged register.** No BRSF tool moves story and task states of a register that is one merged file and writes the next version with an audit note. I wrote `move_state.py` (reads a JSON of task ids with audit notes and story ids, writes the next version) and `closure_make_v1_0_0.py`, `final_observations_make_v1_0_0.py` (observations for every objective, then the closure statements). Wanted: a native tool for the same steps.
2. **Merging delta versions into one file.** The archive tool reads one file; I wrote a merge script (latest value for state, outcome, status and dates; every other statement kept).
3. **Archive gate, two hidden preconditions.** (a) The Lineage statement must carry `lineageArchived false` on its first line; the tool refuses with a message that does not say the register must be hand-edited for it. (b) The register root must not own a definition of done, a commitment or `belongsToLineage`; otherwise the tool leaves 6 statements and the pointer set live. Wanted: a check that names these before closure, and a shape for them.
4. **Objective targets written at planning can be unreachable.** One target counted the keys of a file that holds two non-example keys, so no deliverable could reach it; two others counted files the mission itself plans. Found only at final observation. Wanted: a planning-time dry run of every measurement query against the baseline.
5. **Stand-in for an external service.** The generic chapter-deck builder knows no stand-in for a service that cannot be reached; a patch script adds the facts to the manifest afterwards.
